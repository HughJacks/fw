# fw

A free-writing app growing slowly into a block-and-live-quote PKM, written in the browser (the web editor, the default) or, deprecated, the terminal. **Read `DESIGN.md` first.** It's the technical map: principles, files, where changes go, the data model (schema v17), the architecture, and working on it. Every key is in `KEYS.md`.

- **Build it slowly and without bloat.** Build only what's asked; never build or plan stretch goals unprompted.
- **Functional principles in the code too:** a block is a recursive option type, pure functions, I/O at the edges. Standard library only, except the store's `loro` (`fw_loro.py` is the only module that imports it; installed in `.venv`, and in `tests/.venv` for the tests).
- **The web editor is where new editor work goes;** the terminal editor is deprecated, kept working. The core is `fw_web.py` (the only part that touches the store, through fw_store); the page is `web/` (the running core rebuilds the page when `web/src` changes and restarts itself when `fw_*.py` change, and the open tab reloads itself; still run `npm run build` in `web/` to check a change builds). The data model stays apart from the editor: the page never reads or writes the store itself. Treat a change to it as a change to how someone writes: `tests/run.sh` runs the page's tests too, as the suite "web" (its build, `npm test`, and the browser suite `web/test/e2e.mjs`, scenarios in parallel, each on a fresh store); new browser checks go in a scenario there, waiting on `window.fw.settled()` and placing cursors with `window.fw.select`, never fixed sleeps or DOM ranges; `tests/web_test.py` covers the core.
- **The page is Svelte 5, with runes, because the data is dependent.** State the page shows is `$state`; anything worked out from it (word counts, titles, the trail, what a menu offers) is `$derived`, never recomputed by hand or redrawn imperatively; side effects (measuring, ProseMirror) go in `$effect`. Plain Svelte (not SvelteKit: fw_web.py is the server). ProseMirror stays the editing engine, mounted by a component; everything around it is components. New UI is a `.svelte` component; shared state lives in `*.svelte.js` modules.
- **The web editor's keys live in `web/src/keys.svelte.js`** (`COMMANDS`: each command's id, label, where, default; the user's own bindings over them, kept in `web-keys.json` beside the store, edited on #/keys). Code reads a command's key with `keyOf(id)` and tests an event with `pressed(e, id)`, never a fixed key; defaults are Mac app keys (⌘), off the keys a browser keeps (`KEPT`).
- **No model in fw.** Search by meaning asks an optional service apart from fw (`fw_meaning`, standard library, `$FW_MEANING_URL`, off by default); fw works the same without it.
- **The terminal editor's keys live in `fw_keys.py`** (`KEYMAP`, and what each action does). After changing them, regenerate `KEYS.md` with `python3 fw_keys.py > KEYS.md`; `tests/keys_test.py` fails if you forget.
- **Menu commands follow one pattern:** each is a `Command` in `fw_menu.commands`. Decide two things for every new one: does it **close the menu** after it runs (one-shot actions: Open it, Turn into …) or **stay open** (`stays=True`: toggles and anything you'd do a few of in a row; its label refreshes)? And does it belong **in a submenu** (`group=`, with a `group:<name>` entry that opens it) to keep the top level short? Nested commands still show up when you search for them.
- **Where a change goes:** a new menu command in `fw_menu.py` (a `Command` in `commands`, its method named in `run_command`); mask editing in `fw_mask_ui.py`; blocks selected whole in `fw_blocks.py`; how things are laid out and drawn in `fw_layout.py`; keys in `fw_keys.py`; pure block/draft/mask logic in `fw_block.py`, `fw_draft.py`, `fw_lens.py`; pictures (format, size, the terminal escape) in `fw_image.py`; store writes in `fw_store.py`; a schema change's migration as a step in `fw_migrate.py`; the app loop and the Open it trail in `fw_app.py`; state a mode owns as a field of its record in `fw_state.py` (not a new loose attribute or dict key). New suites use `tests/fwtest.py` (see its docstring).
- **Everything is a block.** Any block type added (text, image, whatever comes next) must work with every block operation: Quote a block (found in the search), Turn into a quote (and open it), Open it, selected whole, copy/cut/paste, undo. Write those operations over the content cases generically (`store.pop_out` takes any content but a quote's; `fw_block.is_whole` names the blocks with nothing to write in), and test a new case through all of them.
- **Undo must revert an action completely,** including whatever it changed in the store.
- **Before installing a change:**
  1. Run `tests/run.sh`.
  2. Make sure no terminal fw session is open: `pgrep -fl "fw_app|fw_edit"` (the web core updates itself).
  3. Back up your store (`freewrites.loro`, `freewrites.json`, its `images/`).
  4. Install, then run `.venv/bin/python fw_store.py migrate` and check the store.
- **`freewrites.loro` (with its copy `freewrites.json`) is your real writing.** Tests use throwaway stores (`FW_DATA`); never write to the real one in tests.
